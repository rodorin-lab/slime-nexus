アーキテクチャ アプローチ

Godot 4 プロジェクト構成の方針を選んでください

A

シーン中心型 (Scene-Centric)

Godotのシーンツリーにすべてを委ねる。各システム（バトル・育成・探索）を独立したシーンとして実装。Godotのドキュメントに最も沿ったオーソドックスな構成。
scenes/ battle/ ← バトルシーン完結 raising/ ← 育成シーン完結 world/ ← 探索シーン完結 ui/ ← UI部品
Godot標準に忠実 シーン単体でテストしやすい システム間の状態共有が複雑になりがち スライムデータの受け渡しが煩雑
B

Autoload重視型 (Service Layer)

ゲームロジックをAutoload（グローバルシングルトン）に集約。シーンは描画専用の薄い層にする。Unity的なManagerパターン。
autoloads/ GameManager ← ゲーム全体の状態 SlimeManager ← スライム管理 BattleSystem ← バトルロジック SaveSystem ← セーブ/ロード scenes/ ← 薄い表示レイヤーのみ
グローバルアクセスが容易 システム間連携がシンプル Autoloadが肥大化しやすい テストが難しくなる
C

ハイブリッド型 (Resource + Autoload) 推奨

Godot 4のResourceシステムでスライムデータを定義し、最小限のAutoloadで状態管理、シーンで描画。各レイヤーの責務が明確で拡張しやすい。
resources/ slime_data/ ← SlimeDefinition.tres（種族定義） evolution/ ← EvolutionPath.tres（進化ルート） autoloads/ GameState ← 薄い状態管理のみ SaveSystem ← セーブ/ロード scenes/ world/ ← 3D探索マップ battle/ ← バトル演出 raising/ ← 育成UI
Godot 4のResourceが最大活用できる スライムデータをInspectorで編集可能 レイヤーが明確で保守しやすい 設計の初期コストがやや高い
